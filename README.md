# Clarius RAW Data Downloader

A standalone Windows and macOS desktop application for downloading and tracking RAW ultrasound capture archives from **Clarius Cloud**.

The application packages the Python runtime, Playwright, and Chromium for the end user. A user who receives the Windows installer or macOS DMG does **not** need to install Python, Playwright, Chrome, or any development tools.

> **Intended use:** internal/research workflows with an authorized Clarius account and an approved data-storage location. The application does not bypass Clarius permissions.

---

## What this project provides

The repository contains three related parts:

1. **The desktop application** — a GUI for entering Clarius credentials, choosing the download destination, selecting a synchronization mode, and monitoring progress.
2. **The downloader engine** — the automated Clarius exam/capture discovery, RAW archive download, resume, date resolution, and synchronization-state logic.
3. **Build and distribution files** — GitHub Actions workflows and packaging definitions that create standalone Windows and macOS downloads.

The main goal is to turn the original automated download script into an application that can be handed to another authorized user without requiring them to edit Python code.

## Main features

- Standalone GUI; end users do not edit source code.
- Clarius email/password entered at runtime.
- Password is **not saved** to local settings.
- Active and archived exam synchronization supported.
- **Normal sync** mode for incremental downloading after the last successful synchronization.
- **Patient range rerun** mode for controlled re-downloads, testing, and recovery.
- Patient-range runs do **not** change the normal synchronization timestamp.
- Separate synchronization state for active and archived exams.
- Resume protection for existing non-empty RAW `.tar` archives.
- Optional deliberate replacement of existing RAW archives.
- Safe stopping so an interrupted run does not incorrectly advance synchronization state.
- Automatic study-folder and image-folder creation.
- Stable capture identification using capture UUID markers.
- Daily operational logs and crash logs.
- Detailed date-resolution diagnostics for troubleshooting.
- Windows installer build plus Apple Silicon and Intel macOS DMG builds.
- Packaged Chromium so end users do not need a separate browser installation.
- Automated source, packaged-app, browser, installer/DMG, and delivery-artifact checks in GitHub Actions.

## Download modes

### 1. Normal sync

Normal sync is intended for routine operation.

The application reads the last successful synchronization timestamp for the selected download folder and processes exams that can be reliably identified as newer than that cutoff.

Important safety behavior:

- Normal sync uses a resolved exam/acquisition date rather than simply assuming that an exam with a missing date is new.
- If a trustworthy date cannot be resolved, the exam is not blindly treated as a new exam.
- Exams at or before the current `last_sync` boundary are skipped.
- `last_sync` advances only after a fully successful normal-sync run.
- A stopped or partially failed run does not advance the successful-sync timestamp.

This prevents an old exam with missing or misleading date metadata from being downloaded solely because the date could not be interpreted correctly.

### 2. Patient range rerun

Patient range mode is intended for:

- testing a known patient;
- recovering selected patients;
- re-running a controlled range;
- checking the application before a large normal sync.

The selected patient number range is processed independently of the normal synchronization cutoff.

**Patient range mode never updates `last_sync`.**

## Typical output structure

Downloaded study folders are created directly inside the selected download folder. A study may look similar to:

```text
<download folder>/
├── P403_TL_02_Aug_21-26-REB16236-403/
│   ├── P403_Image_1/
│   │   ├── <capture-uuid>.tar
│   │   └── _CAPTURE_UUID.txt
│   └── P403_Image_2/
│       ├── <capture-uuid>.tar
│       └── _CAPTURE_UUID.txt
│
└── _ClariusDownloader/
    ├── last_sync_active.json
    ├── last_sync_archived.json
    └── logs/
        ├── sync_YYYY-MM-DD.txt
        └── crash_YYYYMMDD_HHMMSS.txt
```

The exact study-folder name is based on the study/patient information and the resolved exam date.

## Synchronization state

The application keeps synchronization metadata under:

```text
<download folder>/_ClariusDownloader/
```

Active and archived exam state are intentionally separate:

```text
last_sync_active.json
last_sync_archived.json
```

Example:

```json
{
  "last_sync": "2026-08-01T00:00:00"
}
```

For an existing workflow, use the application's **Import prior state** function with a known-good state file when appropriate. Manual timestamp editing is not recommended for normal operation because an incorrect cutoff can cause exams to be skipped or reconsidered.

## Quick start for end users

### Windows

1. Download `ClariusRawDownloader-Setup.exe` from the approved release/build source.
2. Run the installer.
3. Open **Clarius RAW Data Downloader** from the Start menu or desktop shortcut.
4. Enter the authorized Clarius account email and password.
5. Confirm the institution ID, study code, and download folder.
6. Test with a small known patient range before the first large normal sync.

### macOS

1. In **Apple menu → About This Mac**, determine whether the Mac is Apple Silicon or Intel.
2. Download the matching DMG.
3. Open the DMG.
4. Drag `ClariusRawDownloader.app` to **Applications**.
5. Open the application from Applications.
6. Enter the authorized Clarius account information and perform a small known-patient test first.

See [`USER_GUIDE.md`](USER_GUIDE.md) for detailed end-user instructions and the handoff acceptance checklist.

---

## Recommended first test

Before relying on the application for routine synchronization:

1. Choose **Patient range rerun**.
2. Use one approved, known patient number as both the start and end of the range.
3. Keep **Show browser** enabled for the first test.
4. Keep **Replace existing RAW archives** disabled.
5. Start the download.
6. Confirm that expected study/image folders and non-empty `.tar` files are produced.
7. Run the same patient range again and confirm that existing non-empty archives are skipped.
8. Only after this succeeds, proceed to a controlled normal sync.

## Building the standalone downloads with GitHub Actions

The recommended build method is GitHub Actions so the maintainer does not need to maintain local Windows and macOS build machines.

### Windows

Go to:

**GitHub → Actions → Build Windows installer → Run workflow**

After the workflow is fully green, download the artifact named approximately:

```text
ClariusRawDownloader-Installer
```

Extract the artifact ZIP to obtain:

```text
ClariusRawDownloader-Setup.exe
```

### macOS

Go to:

**GitHub → Actions → Build macOS apps → Run workflow**

The workflow builds both architectures independently:

```text
Build Apple-Silicon
Build Intel
```

When both are green, download the appropriate artifacts:

```text
ClariusRawDownloader-macOS-Apple-Silicon
ClariusRawDownloader-macOS-Intel
```

Extract each GitHub artifact ZIP to obtain its `.dmg` file.

The macOS build embeds an architecture-matched Playwright Chromium runtime. Chromium is copied into the final `.app` after the main PyInstaller application bundle is created, avoiding unnecessary PyInstaller rewriting of the nested Chrome binary.

See [`CLOUD_BUILD.md`](CLOUD_BUILD.md) for the complete build procedure.

---

## Rebuilding after code changes

If application behavior changes — especially changes to:

```text
app.py
clarius_downloader_core.py
```

— previously generated installers do **not** update automatically.

Re-run the relevant GitHub Actions workflows and distribute the newly generated files:

```text
Update source code
        ↓
Commit / push to GitHub
        ↓
Build Windows installer
        ↓
Build macOS Apple Silicon + Intel
        ↓
Test the new artifacts
        ↓
Distribute the new installer/DMGs
```

Windows and macOS use the same downloader core, so a change to `clarius_downloader_core.py` should normally be followed by rebuilding **all three end-user downloads**.

## Testing performed by the build workflows

The build workflows are designed to fail before publishing an artifact when important checks fail.

Depending on the platform, checks include:

- Python unit tests;
- source `--self-test`;
- PyInstaller application build;
- packaged application `--self-test`;
- packaged Chromium `--browser-self-test`;
- Windows installer creation and installed-app verification;
- macOS application code-signature verification;
- DMG creation and verification;
- mounting the final DMG;
- copying the app out of the DMG to mimic user installation;
- re-running application and browser self-tests on the final delivered app.

A green GitHub Actions run is therefore more meaningful than merely confirming that PyInstaller produced a file.

## Security and privacy

- Do **not** hard-code Clarius passwords in the source code.
- Do **not** commit credentials, private keys, certificates, temporary download URLs, or authentication cookies to GitHub.
- The password entered in the GUI is session-only and should not be persisted.
- Use only an authorized Clarius account.
- Save downloaded study data only to a location approved for the relevant research/data-governance requirements.
- Review logs before sharing them externally.
- Do not attach RAW patient data to public GitHub issues.
- Keep the repository private unless public release has been explicitly approved by the responsible institution/team.

## Windows signing and macOS notarization

Internal builds may be unsigned or only locally/ad-hoc signed.

### Windows

An unsigned internal installer can trigger Microsoft SmartScreen. For wider routine distribution, institutional code signing is recommended.

### macOS

Without an Apple Developer ID configuration, the application is built with an ad-hoc signature and macOS may require first-launch approval.

For normal Gatekeeper behavior, configure an authorized **Developer ID Application** certificate and Apple notarization credentials as GitHub repository secrets. See [`MACOS_SIGNING.md`](MACOS_SIGNING.md).

Never commit signing certificates, private keys, or signing passwords to the repository.

## Troubleshooting

Useful files are stored under:

```text
<download folder>/_ClariusDownloader/logs/
```

When diagnosing a problem, the most useful information is usually:

- whether the run was Normal Sync or Patient Range;
- active vs archived mode;
- the current `last_sync` value;
- the patient/study identifier involved;
- the final portion of the relevant `sync_YYYY-MM-DD.txt` log;
- the exact GitHub Actions step/error if a build failed.

For date-selection problems, enable **Detailed date-resolution log** and reproduce the issue using a small approved test case.

The application depends on Clarius Cloud behavior and may require maintenance if Clarius changes:

- login/authentication flow;

- HTML page structure;
- date fields;
- RAW archive endpoints;
